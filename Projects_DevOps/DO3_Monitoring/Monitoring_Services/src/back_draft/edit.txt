## Что значат ключевые части конфига

**`alertmanager.yml`:**
- `route: group_by: ['alertname']` — если сработает сразу несколько алертов с одним и тем же именем (например, `HighServiceCPU` на трёх сервисах разом) — они склеятся в **одно** уведомление, а не завалят вас тремя письмами подряд.
- `group_wait: 10s` — подождать 10 секунд перед первой отправкой группы, вдруг за это время придёт ещё что-то похожее, чтобы объединить.
- `repeat_interval: 1h` — если проблема не устранена, повторно напомнить через час (иначе шлёт один раз и молчит).
- `inhibit_rules` — если уже горит `critical`-алерт по конкретному инстансу, не дублировать по нему же `warning`-алерт (чтобы не заваливать оповещениями по одной и той же причине).

**`alert_rules.yml`:**
- `for: 1m` / `for: 2m` — условие должно быть истинным **непрерывно** это время, прежде чем алерт реально станет `firing`. Без этого любой мгновенный всплеск CPU на долю секунды считался бы инцидентом.
- 4-е правило `ServiceDown` (`up == 0`) я добавил сверх вашего исходного списка — это стандартный и очень полезный алерт: `up` — служебная метрика, которую сам Prometheus создаёт для каждой цели, `0` означает, что цель не отвечает на scrape (сервис упал/недоступен). Если не нужен — просто удалите этот блок.

Не забудьте перед деплоем поправить в `alertmanager.yml`: email/пароль приложения Gmail и `bot_token`/`chat_id` для Telegram — сейчас там заглушки.

## Панели на Prometheus (метрики) — тип панели "Stat"

Для 1–3, 8, 10–14: выбираете справа тип панели **Stat** (показывает одно большое число) — подходит, когда нужно просто "количество чего-то".

| № | Название панели | Query (вставить в поле запроса) |
|---|---|---|
| 1 | Количество нод | `count(node_uname_info)` |
| 2 | Количество контейнеров | `count(container_last_seen)` |
| 3 | Количество стеков | `count(count by (container_label_com_docker_stack_namespace) (container_last_seen))` |
| 8 | Количество CPU | `count(node_cpu_seconds_total{mode="idle"})` |
| 10 | Отправлено сообщений RabbitMQ | `rabbitmq_messages_sent_total` |
| 11 | Обработано сообщений RabbitMQ | `rabbitmq_messages_processed_total` |
| 12 | Количество бронирований | `bookings_created_total` |
| 13 | Запросов на gateway | `gateway_requests_total` |
| 14 | Запросов на авторизацию | `auth_requests_total` |

## Панели на Prometheus — тип панели "Time series"

Для 4, 5, 6, 7 — берите тип **Time series** (график изменения во времени), т.к. это метрики, где важна динамика, а не одно число.

**4. Использование CPU по сервисам**
```
sum(rate(container_cpu_usage_seconds_total{name!=""}[5m])) by (name)
```
Тип: **Time series**. В поле **Legend** (внизу редактора запроса) впишите `{{name}}` — чтобы на графике каждая линия подписывалась именем сервиса, а не сплошным номером.

**5. Использование CPU по ядрам и узлам**
```
sum(rate(node_cpu_seconds_total{mode!="idle"}[5m])) by (instance, cpu)
```
Legend: `{{instance}} cpu{{cpu}}`

**6. Затраченная RAM**
```
node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes
```
Справа в **Field → Unit** выберите **Data → bytes(IEC)** — тогда график покажет "1.2 GiB" вместо "1288490188".

**7. Доступная и занятая память** — тут **два запроса в одной панели**:
- Нажмите **+ Query** (добавить второй запрос) в редакторе панели:
  - Query A: `node_memory_MemAvailable_bytes`, Legend: `Доступно`
  - Query B: `node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes`, Legend: `Занято`
- Тип: **Time series**, Unit: **bytes(IEC)** (как в п.6).

## Панель 9 — Доступность google.com (Stat)

```
probe_success{instance="https://google.com"}
```
Тип: **Stat**. Чтобы вместо `1`/`0` показывало текст "UP"/"DOWN":
- В редакторе панели справа откройте **Value mappings → Add value mappings**
- Добавьте: значение `1` → текст `UP`, цвет зелёный
- Добавьте: значение `0` → текст `DOWN`, цвет красный

> ⚠️ Обратите внимание: если ваш `blackbox_exporter` в `prometheus.yml` настроен не на `google.com`, а на ваши внутренние эндпоинты (как мы делали ранее — `gateway-service`, `session-service` и т.д.) — тогда фильтр `{instance="https://google.com"}` вернёт пусто. Проверьте реальное значение label `instance` через **Explore** (см. ниже) и подставьте правильный адрес, либо уберите фильтр совсем — `probe_success` без `{}` покажет все проверяемые эндпоинты сразу.

## Как проверить запрос перед тем, как класть его в панель

Полезная привычка — не гадать сразу в редакторе панели, а сначала проверить запрос в **Explore** (иконка компаса в левом меню): выбираете источник (Prometheus или Loki), вставляете запрос, жмёте **Run query** — сразу видно, есть ли данные и как выглядят метки (`instance`, `name`, `service` и т.д.), прежде чем оформлять как панель.
